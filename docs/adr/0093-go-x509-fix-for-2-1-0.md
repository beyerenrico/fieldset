# 0093: Go 1.27.3 for the app image and pins for CVE-2026-111943 (release 2.1.0)
- Status: accepted; amended 2026-11-13 (Postgres server and client pinned to exact versions, minor check; app image
  go-jose and x/net fixes, third-party images refreshed and exceptions renewed)
- Date: 2026-10-21
- Amends: ADR 0071 (binary table, golang and FrankenPHP pins, current exceptions; mailpit gets an exception file).
  The scan policy itself is unchanged.
- Decision by the human (QUESTIONS 77a): "Fix it, then release (Recommended)": "New branch: update Go, Docker CLI,
  FrankenPHP and third-party image versions; dated exceptions only where no fixed image exists. Then rescan, rerun
  all journeys, merge and tag v2.1.0 locally."

## Context
On 2026-10-21 Trivy's database gained CVE-2026-111943 (Go `crypto/x509`, HIGH, fixed in Go 1.26.10 and 1.27.3). The
2.1.0 gate (`milestones/R2.1.md`) found it in every Go binary of the app image (age, age-keygen,
age-plugin-batchpass, Compose and FrankenPHP at Go 1.27.2, the Docker CLI at 1.26.9) and in five of the six
third-party images. The app image allows no exception (ADR 0071).

## Decision
**App image** (`docker/app/Dockerfile`, `docker/app/binaries.json`):

**Third-party images** (`distribution/release.json`, Docker Hub tags checked 2026-10-21):

  built with Go 1.27.3 (Trivy build info, both platforms), and its amd64 image no longer has the libssl3t64 finding,
  so that entry (CVE-2026-84782) is removed. CVE-2026-63209 (klauspost/compress 1.18.0) is still in 2026.10.2; its

- postgres 16.15-alpine (gosu, Go 1.24.6), gotenberg 8.38.1 (Go 1.27.1), mailpit v1.31.6 (Go 1.27.2) and caddy
  2.11.7 (Go 1.26.8) are the newest images; none has a release built with a fixed Go. Each gets one dated entry for
  CVE-2026-111943, scoped by path (`usr/local/bin/gosu`; `usr/bin/gotenberg` and `usr/bin/pdfcpu`; `mailpit`;
  `usr/bin/caddy`), expiring **2026-11-20**: 30 days, because the fix exists upstream and only the image release is
  missing (ADR 0071). gosu does not get 90 days: no reachability analysis was made for this CVE.
- mailpit had no exception file; it now has `distribution/trivy/mailpit.trivyignore.yaml`, and
  `ImageScanPolicyTest` lists it among the services with a file.

## Verification
Trivy 0.76.0 with the release.yml flags (DB of 2026-10-21): the app image without exceptions, every third-party image
with only its own file, both platforms: all pass (`milestones/evidence/R2.1/trivy.txt`).

## Consequences
- Exceptions now expire on 2026-11-17 (gotenberg, caddy: older entries), 2026-11-20 (the CVE-2026-111943 entries,
  cloudflared) and 2027-01-16 (postgres, older gosu entries). A release after 2026-11-17 needs new pins or renewed
  entries.
- Replace each new entry as soon as the image is rebuilt with Go ≥ 1.26.10 / 1.27.3.

## Alternatives considered
- **Exceptions for the app image:** forbidden by ADR 0071; the binaries can be rebuilt.
- **Building gosu, Gotenberg, Mailpit or Caddy ourselves:** would make us maintain forks of third-party images;
  ADR 0071 accepts dated exceptions for this case.
- **90 days for gosu (as its older entries):** needs a reachability analysis that was not made.

## Amendment 2026-11-13: one Postgres server and one client version everywhere, and a minor check
- **Why.** Two restore failures on GitHub's runners, both reproduced with throwaway containers on 2026-11-13 (dump
  with the app's flags from a migrated database, restore with `--exit-on-error`):

  | Run | Source server | `pg_dump` / `pg_restore` | Target server | Result |
  |---|---|---|---|---|
  | CI 41776257535 (`php-tests`, 2026-11-04) | 16.15 | 18.7 | 16.15 | fails: `unrecognized configuration parameter "transaction_timeout"` |
  | Nightly 43402721640 (J09, 2026-11-13) | 16.16 | 16.15 | 16.15 | fails: `unrecognized parameter "pg_attver"` |
  | | 16.16 | 16.16 | 16.15 or 16.16 | passes |
  | | 16.15 | 16.15 or 16.16 | 16.15 or 16.16 | passes |
  | Published 2.1.0 (image client 16.15-1.pgdg12+2, manifest server 16.15) | 16.15 | 16.15 | 16.15 | passes |

  CI: `ubuntu-latest` became Ubuntu 26.04, whose `postgresql-client` is 18; the job's comment still assumed 16 on
  24.04. Nightly: PostgreSQL 16.16 was released on 2026-11-12 (Docker Hub `16.16-alpine` and `16-alpine` pushed
  22:13 UTC). J09 starts 1.0 from its own `compose.yaml`, which runs the floating `postgres:16-alpine`, so its server
  became 16.16; the harness image came from the build cache, with the client of an earlier day. A 16.16 server keeps
  `pg_attver=<n>` in `pg_attribute.attoptions` of every column. pg_dump 16.15 copies column options into the dump
  (`ALTER COLUMN … SET (pg_attver=…)`), and the instance's 16.15 server refuses the option; pg_dump 16.16 leaves it
  out. The 16.16 release notes do not name the option: this is what the containers show, not a documented change.
- **Published instances.** 2.1.0 pins server and client at 16.15, and that pair passes. It fails in one case: `fieldset
  adopt` of a 1.0 stack whose `postgres:16-alpine` was pulled after 2026-11-12, because 2.1.0's pg_dump 16.15 dumps a
  16.16 server. The restore drill then fails (exit 4) and `fieldset restore` of that backup rolls back before the swap
  (exit 5), as in the nightly log.
- **Change.**
  - Server: `compose.yaml` and the `postgres` services of `ci.yml` run the manifest's image by tag and digest
    (`docker.io/library/postgres:16.15-alpine@sha256:721873c3…`), as `docs.yml` already did. `PostgresServerPinTest`
    fails when one of them differs from `distribution/release.json`.
  - Client: `postgresql-client-16=16.16-1.pgdg12+1` in `docker/app/Dockerfile` and `docker/ci/Dockerfile`;
    `php-tests` adds PGDG for the runner's Ubuntu release and installs `16.16-1.pgdg<release>+1`
    (`PG_CLIENT_VERSION`), with `/usr/lib/postgresql/16/bin` first on `PATH`. `binaries.json` records 16.16.
    `ImageBinariesTest` fails when an install names no exact version or the three places differ.
  - `release:check-pg-dump` (ADR 0091, R39) also refuses a client whose minor is below the server's within the same
    major, naming both versions. A newer client major passes as before.
- **Consequences.**
  - A Postgres update is now an edit: the server pin in `release.json` (the test names the other files), the client
    version in three places. The client must be raised first or together with the server.
  - PGDG's index listed three minors (16.14 to 16.16) and one package revision of each on 2026-11-13. If that is
    its rule, a rebuilt package (`+2`) or a fourth minor removes the pinned version, and the image build fails until
    the pin is raised.
  - `libpq5` and `postgresql-client-common` stay "PGDG current": the client package depends on them without an exact
    version, and the failure was in pg_dump itself.
- **Not covered.** 1.0's server floats and cannot be pinned from here. When 16.17 is released, an adopt with a
  16.16 client can fail the same way, and J09 will show it in the nightly run. `fieldset adopt` does not compare its
  pg_dump with 1.0's server minor. A newer client major still passes `release:check-pg-dump`, although the first row
  of the table shows that an 18 client cannot restore its own dump into a 16 server.
