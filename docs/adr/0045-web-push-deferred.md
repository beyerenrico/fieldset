# 0045: Web push for the Field App is deferred past 1.0
- Status: accepted
- Date: 2026-10-22

## Context
§8.9 lists the notification channels: in-app (Filament database notifications, the Field App's notification
center) and email. It adds: "Web push for the installed PWA comes in v1.0; on iOS it needs the home-screen install
(unverified, check before M8)." PLAN M8-T08 narrows this: build web push only if it is feasible without new
infrastructure, otherwise record it as deferred.

What web push would need here (checked in the code base, 2026-10-22):
- **Keys and config:** a VAPID key pair (P-256) per instance, generated at install, stored as secrets, rotated
  with care because existing subscriptions are bound to the public key.
- **Server sending:** RFC 8291 payload encryption (ECDH + HKDF + aes128gcm) and an RFC 8292 VAPID JWT (ES256) for
  each push. PHP has no built-in for this. The usual package is `minishlink/web-push` (MIT), a new dependency with
  its own crypto stack. Hand-rolling the encryption is possible with ext-openssl, but it is security-sensitive code
  without a conformance suite in this repo.
- **Outbound calls:** pushes go to the browser vendors' push services (FCM, Mozilla autopush, Apple). Every call
  must pass the SSRF guard (§11) with an allow-list of push-service hosts, plus retry and expiry handling
  (404/410 removes a subscription).
- **Data:** a `push_subscriptions` table (user, device, endpoint, keys, user agent, created/last used), tenant and
  GDPR handling (user export and erasure, device revocation in ADR 0035 must drop subscriptions).
- **Field App:** the service worker is generated by Workbox (`strategies: 'generateSW'`,
  `resources/field-app/src/lib/pwa/pwa-options.ts`). Handling `push` and `notificationclick` means switching to
  `injectManifest` (a hand-written service worker) or importing a script into the generated one, both of which
  touch the offline machinery of ADR 0035. A permission prompt, subscribe/unsubscribe UI and a per-event
  "push" channel in the preferences (`ChannelPreferences`) complete it.
- **iOS:** Safari supports web push only for web apps added to the home screen (WebKit announced it for iOS and
  iPadOS 16.4 in 2023; not verified on a device here). Installed-PWA detection and instructions would be needed.

## Decision
Web push is **deferred** past 1.0. It is not trivially doable without new infrastructure: it needs instance
secrets, a new dependency or hand-written crypto, outbound calls to third-party push services, a new table with
GDPR handling, and a custom service worker. None of it is built now.

The 1.0 channels stay in-app and email, both with per-user, per-event preferences (§8.9 AC).
The Field App's notification center polls while the app is open, and the email channel covers the
"app closed" case.

## Consequences
- §8.9's "Web push … comes in v1.0" is not met; the 1.0 release notes list it as a known gap, and
  `docs/agent/QUESTIONS.md` keeps it for a human decision on priority.
- When it is picked up, the order is: ADR for the library choice (`minishlink/web-push` vs. own code) and the
  push-service allow-list in the SSRF guard; migration and model; `injectManifest` service worker with a
  `push`/`notificationclick` handler and tests for the offline paths; preferences channel; device revocation and
  GDPR export/erasure; E2E with a mocked push service.
- Nothing in 1.0 depends on push, so adding it later needs no data migration of existing notifications.
