# 0036: SSO per organization (OIDC, SAML, discovery, JIT, enforcement)
- Status: accepted
- Date: 2026-10-18

## Context
§8.7 requires per-organization OIDC (Entra, Google Workspace, generic: Keycloak/Authentik/Zitadel), SAML 2.0, home-realm discovery over DNS-verified domains, JIT with claim mapping, enforced SSO with a break-glass Owner, and audit of every auth event. §8.9 adds `sso_misconfigured`. §16 allows only Keycloak in Docker and a fake DNS resolver.

Today:
- /admin uses the Filament login.
- The Field App uses headless Fortify under /auth (ADR 0019).
- There is one session and one TOTP secret (ADR 0016), with 30-day rolling sessions (ADR 0018).

## Decision
### Packages (verified 2026-10-17/18 on Packagist and from the tagged sources; MIT/BSD-3)
- laravel/socialite ^5.31 and socialiteproviders/manager ^4.10.
- socialiteproviders/openidconnect ^1.0.1 handles all OIDC providers. It provides:
  - discovery, JWKS with key-rotation refetch, and an algorithm allow-list;
  - checks of iss, aud, azp, exp, nbf and iat, a one-time nonce, at_hash, and PKCE S256;
  - Entra and Google flavors.

  It requires firebase/php-jwt ^7.
- socialiteproviders/saml2 ^4.10 with an explicit `litesaml/lightsaml: ^4.7.2`. That version carries the XSW fixes and pulls xmlseclibs ≥ 3.1.5. We accept a release that is one day old because it is a security fix.
- Rejected:
  - socialiteproviders/keycloak and microsoft-azure: they use userinfo/Graph and validate neither the id_token nor a nonce.
  - filament-socialite: static providers from config, admin panel only.

### Data model
- `identity_providers` (tenant-scoped, one per organization in v1):
  - uuid (the public id in URLs), type oidc|saml, name, status draft|active|error|disabled;
  - `encrypted:array` config (flavor, issuer, tenant, client id, scopes, claim and attribute names, SAML metadata);
  - client_secret (encrypted, write-only);
  - jit_enabled, default role and group, enforce_sso, break_glass_user_id, force_reauth, last error and last success.
- `sso_domains`:
  - domain (lower-case, punycode, exact match), verification token, verified_at, check bookkeeping;
  - unique per (organization, domain);
  - a partial unique index on domain `WHERE verified_at IS NOT NULL`: many organizations may claim a domain, only one can verify it.
- `identity_provider_mappings`: a claim value maps to a role XOR a group. Owner is never a mapping target.
- `external_identities`: user, provider, subject, issuer, last email, last login; unique on (provider, subject).
  - Identities are keyed by provider, not issuer, because an organization controls its own IdP's discovery document. It could publish another organization's issuer.

### Runtime providers
- A factory builds an OIDC or SAML provider per request from the stored config. Every provider uses an SSRF-guarded HTTP client: public addresses only, a pinned resolution, no redirects, https.
  - `sso.allow_insecure_idp` allows http and private hosts, for dev and CI only.
- Flavor rules:
  - Entra requires a tenant GUID and asserts `tid`.
  - Google requires the `hd` claim to be a verified domain and `email_verified=true`.
  - Generic OIDC requires email_verified, unless an audited opt-in is set.
- State, nonce and code verifier live in the session. The return target is an enum (`admin` | `app`) and is never taken from the request.

### Identity resolution and JIT (one path for OIDC and SAML, `CompleteSsoLogin`)
1. Find the user by (provider, subject).
2. Otherwise link or create the user by email. This requires the domain to be verified by the provider's organization and the email to be verified (claim, Entra UPN, or a signed SAML assertion).
3. Deactivated users and memberships are refused; SSO never reactivates them. An invited membership is activated.
4. A non-member gets a membership with the default role (Field Worker if unset) and the default group when JIT is on; otherwise the login is refused with `not_member`.
5. Mappings re-sync on every login as an IdP-managed set:
   - Roles and groups that are mapping targets follow the claim.
   - Manual assignments and Owner are untouched.
   - A missing claim skips the sync and is audited.
6. The IdP may change a user's email only within verified domains, and only to an address that is free.

- JIT users get a random password hash and a verified email.
- SSO logins skip local MFA (the IdP's job); `amr` is audited.
- After login the session is regenerated. The admin client returns to the panel. The app client returns to `/app/login?sso=ok`, or `?sso_error=<code>` on failure.

### Home-realm discovery
- `HomeRealmDiscovery::discover(email, client)` works at domain level only: verified domain → organization → provider → redirect URL; otherwise password. It never reveals whether a user exists and is throttled.
- Admin: an email-first Filament login. A "Sign in with a password" link supports break-glass and non-enforcing organizations.
- Field App: an email step calls `POST /auth/sso/discover` and gets `{mode: password}` or `{mode: sso, redirect_url, organization, enforced}`. On return, the existing completeLogin runs (device registration, /me; ADR 0035).

### Enforcement
- `PasswordAuthGate` refuses password login and password reset before any password check when the email's domain is verified by an organization that enforces SSO. It covers:
  - the Fortify login (422 `sso_required`) and the Filament login;
  - the Fortify and Filament reset flows;
  - invitation acceptance, which goes to SSO;
  - the model's reset notification, as a backstop.
- Break-glass: one designated Owner per provider. It must be an active Owner with confirmed MFA when enforcement is switched on and at every login; otherwise the login is refused and `sso_misconfigured` fires. Each use is audited and notified.
- Switching enforcement on requires:
  - a verified domain;
  - an active provider (a successful test login);
  - a valid break-glass Owner;
  - an actor who is the break-glass Owner or already has a linked identity, which prevents self-lockout.
- Enforcement follows the email domain. It therefore applies to that user in every organization, and members on other domains keep passwords.

### Logout
Local logout only. There is no RP-initiated logout or SAML SLO in M7. A per-provider `force_reauth` sends `prompt=login` for shared devices.

### SAML
- SP metadata: `GET /auth/sso/{uuid}/saml/metadata`. ACS: `POST /auth/sso/{uuid}/saml/acs`. The IdP comes from a metadata URL or pasted XML.
- The ACS runs without a session or CSRF check, because a cross-site POST carries no Lax cookie and must not overwrite the session. The flow:
  1. RelayState is a one-time flow id bound to the initiating session.
  2. The ACS validates the response statelessly.
  3. It stores a one-time encrypted ticket.
  4. It answers 303 to `GET /auth/sso/saml/complete`, where the session cookie is present.
  5. That route checks the binding and runs CompleteSsoLogin.
- IdP-initiated SSO is not supported.

### Audit, notifications, checks
- `auth.login` gets `method` (password|sso|break_glass) and `provider`.
- New events: `auth.sso_failed`, `auth.sso_refused`, `auth.password_login_blocked`, `auth.password_reset_blocked`, `auth.break_glass_login`, `sso.user_provisioned`, `sso.identity_linked`, `sso.provider_*`, `sso.domain_*`, `sso.enforcement_changed`, `sso.misconfigured`, and role/group changes with the source `sso`.
- `NotificationEvent::SsoMisconfigured` goes to Owners and Admins at most once per provider and reason every 6 h.
- Scheduled checks:
  - `sso:check-providers` runs hourly.
  - `sso:recheck-domains` runs daily and unverifies a domain after 3 misses in a row.

### Domain verification
TXT record `_form-schema-app-verification.<domain>` = `form-schema-app-verification=<token>`, read through `TxtRecordResolver`:
- dns_get_record in production;
- a config-backed fake in dev and CI;
- a fake in tests.

### Keycloak (dev and CI)
- Image `quay.io/keycloak/keycloak:26.7.5` (verified on Quay, pushed 2026-09-30).
- It runs in compose.dev.yaml under the profile `sso` with `start-dev --import-realm`, and the CI e2e job sets `COMPOSE_PROFILES=sso`.
- The realm `docker/keycloak/realm-form-schema.json` contains:
  - an OIDC client (PKCE S256, groups mapper);
  - a SAML client (signed assertions, email NameID, email and groups attributes);
  - users with names and verified emails.

### Testing
- Fakes: a fake OIDC IdP (RSA key, discovery, JWKS, signed id_tokens), a fake SAML IdP (signed responses, XSW fixtures), a fake TXT resolver and a fake host resolver.
- Playwright drives Keycloak for the §8.7 AC.

## Consequences
- One IdP per organization.
- If the IdP is down while enforcement is on, only the break-glass Owner can sign in with a password.
- Classifying failures depends on the package's exception messages, pinned by unit tests.
- Callback URLs use the provider uuid, so renaming an organization never breaks a registered redirect URI.
- The installed iOS PWA leaving its scope for an external IdP is not covered by E2E (QUESTIONS).

## Amendment 2026-10-18: implementation notes
- **Missing groups claim** (deviation from the "skip" rule above): when the configured groups claim or attribute is absent, it counts as "no groups". Keycloak omits `groups` for users without groups, and stale IdP-managed roles would be the worse failure. Owner is never a target. Other missing claims are still skipped. Both cases are audited (`treated_as: empty|skipped`).
- **SAML package gaps, closed in `AppSaml2Provider`:**
  - Problems found:
    - socialiteproviders/saml2 4.10 does not check the Audience;
    - LightSAML ignores the location criteria, so the Recipient check accepts any URL;
    - the replay check runs before the signature check.
  - Added:
    - Audience, InResponseTo, Destination and bearer-Recipient checks;
    - an atomic replay check after the signature check;
    - refusal of DTD and NUL input (XXE) before and after parsing.
  - AuthnRequests are unsigned unless `SSO_SAML_SP_CERTIFICATE`/`KEY` are set.
- **SAML names** fall back to firstName/lastName (or givenName/sn).
- **SSRF guard:** with `sso.allow_insecure_idp` it neither resolves nor pins, so curl uses getaddrinfo, which matters for `keycloak.localhost` inside containers (LEARNINGS #54).
- **Return targets on failure:**
  - admin client: the Filament login with `?sso_error=<code>`, also flashed;
  - app client: `/app/login?sso_error=<code>`.
- **Test mode** returns to the admin page that started it, with the flash `sso.test_result`. Success turns the provider from draft to active.
- `sso.redirect` and `sso.callback` are throttled (30/min), and discovery on the admin login is limited to 10/min.
- **Admin UI:** one Filament page, `/admin/{tenant}/sso`. A connection change (type, flavor, issuer, tenant, client id, metadata) sets the provider back to draft and is refused while enforced; rotating the secret is always allowed. The last verified domain cannot be removed while SSO is enforced. A DNS outage never counts as a recheck miss.
