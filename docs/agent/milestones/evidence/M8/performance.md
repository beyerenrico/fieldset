# M8 performance evidence (M8-T05)

BUILD_PROMPT §11 "Performance targets", the ADR 0037 Builder v2 targets and PLAN M8-T05. Measured 2026-10-17 on
the dev stack with 100k generated submissions in one organization. Raw results are in [`perf/`](perf/); the
scripts are in `scripts/perf/` (see "Reproduce").

## Verdict

| Target | Measured (p95 unless noted) | Result |
|---|---|---|
| Admin pages < 500 ms at 100k submissions | 26 of 27 page types pass. Slowest passing page: the saved report over all 100k submissions, 365 ms (was 651 ms). Reviewer inbox 316 ms (was 420 ms). Explorer searches ≤ 291 ms. | pass, except the classic builder |
| (same) | Classic builder (v1) `forms/{id}/edit`: 1,052 ms with 4.5 MB of HTML | **fail**, known (ADR 0044: no longer the default); see risks |
| API < 300 ms | All 23 series pass, slowest 125 ms (reviewer submission list, was 268 ms). Draft save with a 500-row repeater: 60 ms | pass |
| 10-page PDF < 10 s (queued) | 10 pages (160 lines, 6 photos, signature, 1.5 MB): 2.3 s from dispatch to stored rendition; render alone 1.0 s | pass |
| 300-element form responsive | Builder v2 (310 elements): operation 21 ms (< 50), preview 29 ms (< 300), sync 166 ms (≤ 500), inspector 114 ms (< 400). Field App, 4× CPU: typing 32 ms, next step 51 ms | pass |
| 500-row repeater responsive | Field App, 4× CPU: typing in the last rows 136–168 ms over 4 runs (was 2,800 ms) | pass after fix |
| (same) | Adding the 501st row, 4× CPU: 192–225 ms over 4 runs, median 203 ms (was 2,827 ms) | at the 200 ms line, not clearly met; see risks |
| Field App first load < 3 s, mid-range Android, 4G | Slow 4G (150 ms RTT, 1.6 Mbit/s, 4× CPU): usable after 2.07 s (p50), LCP 1.85 s. Initial JS+CSS 209 kB gzip | pass |
| (same, stricter profile) | Lighthouse "devtools" throttling (562.5 ms RTT, 1.47 Mbit/s, 4× CPU): usable after 3.52 s | **missed by 0.5 s**; see risks |
| Repeat loads instant from cache | 0 kB over the network (service worker), usable after 0.86 s with 4× CPU | pass |

"Responsive" means an interaction (keydown to next paint, Event Timing API) of at most 200 ms on a 4×
CPU-throttled phone profile. That is Core Web Vitals' "good" INP limit; §11 gives no number.

## Setup

- Host: Apple M1 Pro (10 cores), 32 GB. Docker Desktop VM with 10 CPUs and 15.6 GB, Docker 29.2.1.
- Stack: `COMPOSE_PROFILES=sso docker compose` (compose.yaml + compose.dev.yaml). The app is FrankenPHP 1.13.1
  in classic mode, PHP 8.4.26 with OPcache (`validate_timestamps=0`), and config/routes/views cached by the
  entrypoint. Also PostgreSQL 16.15 (alpine, default settings: shared_buffers 128 MB, work_mem 4 MB, JIT on),
  Valkey 8 and Gotenberg 8.38.1. The `.env` is the dev one (`APP_ENV=local`, `APP_DEBUG=true`), which makes
  the numbers pessimistic: strict models, debug error handler.
- Images were built from a clean context: `git archive HEAD` plus this task's changed files. Other agents'
  unfinished work in the shared tree was therefore left out of the measured image. The "before" image is the
  stack image built from HEAD at the start of the task.
- The scheduler was stopped while the load data was present. Its `documents:sweep` would otherwise render PDFs
  for the ~22k generated submitted/in-review submissions that have no rendition, every 5 minutes.
- Clients: Chromium 1248 (Playwright 1.64, headless) and Node 24.18. All requests come from one client, one
  after another. Every series runs only when the host's 1-minute load average is below 5. Three other agents
  ran test suites on the same machine; their runs took the load to 40 and invalidated a first API run, which was
  discarded. The load at the start of each series is recorded in the JSON files. Kept series started at a load
  of 2.2–4.9.

## Method

| Target | Script | How |
|---|---|---|
| Admin pages | `admin-pages.mjs` | Per page: 3 warm-up and 30 measured navigations as owner or reviewer. **doc** = request start to last HTML byte (Navigation Timing). **Livewire** = slowest Livewire request the page fires while loading (lazy widgets). **complete** = navigation start to the last of those responses. Searches typed into the table: Livewire round trip, 30 per term class |
| API | `api.mjs` | 3 warm-up and 30 requests per endpoint. Field App sessions call from inside the signed-in app page with the app's headers (`fetch` + body read). The integration token calls from Node with a Bearer header. The API allows 240 requests per minute and user; the script waits out 429s and does not count them |
| PDF | `pdf.php` (runs in the app container) | One submitted service report with 160 lines, six 1600×1200 JPEG photos and a signature → 10 pages. 10× `RenderSubmission` inline (HTML → Gotenberg → storage), then 10× `GenerateRendition` dispatched to Horizon, timed until the rendition row exists |
| Builder v2 | `builder-v2.mjs` | Canvas builder of "Perf 300" in desktop Chromium. Operations: keyboard moves of a grabbed element, pick up + drop, undo and redo, from the keydown to the next frame; real key presses also through the Event Timing API. Preview: from the move key until the sandboxed preview shows the new order. Sync: the autosave `sync` round trips. Inspector: Enter on a card until the inspector shows it |
| Field App | `field-app.mjs` | Bundle sizes from `public/app` (gzip -9). First load: Pixel 7 viewport, cold cache, throttled through CDP (network + `Emulation.setCPUThrottlingRate` 4). Reports FCP/LCP (observers), the time until the login form or the home greeting is usable, long tasks over 50 ms before that (TBT-like), and bytes. Fill: a server draft with 500 repeater rows, and a "Perf 300" draft, filled with real key presses; Event Timing gives each interaction |
| Widget data | `php artisan app:dashboard-benchmark demo --runs=5` | Uncached widget and catalog queries (plans and median ms), as in M5 |

## Regression guards

- Query plans: `ApiListPlanTest` (new) next to `QueryPlanTest`/`SearchPlanTest` (M5). The saved-report entry in
  `QueryCatalog` is now the single combined query.
- Query counts: inbox filter options (1 per request), API list (no per-row task/group/attachment/version
  queries), saved report page (1 aggregate).
- Complexity: the form-schema-js 500-row evaluation budget (linear vs quadratic: 29–41 ms vs 1.1–1.4 s), and
  the instance-list memo (same list for the same data object, a new list for a changed copy).
- Reproducible measurements: `scripts/perf/*` (below), with raw results in `perf/` for comparison.

## Remaining risks and proposals

1. **Classic builder (v1) page: 1.05 s and 4.5 MB.** Filament's Builder renders every block schema into the
   page. ADR 0044 already made the canvas builder (110 ms) the default; v1 opens only on request or for
   forms with an open PDF-import report. Proposal: move the import report, versions table and access settings
   to their own pages (ADR 0044 consequences) and retire v1. Alternatively, lazy-load block forms in v1.
2. **Field App first load under Lighthouse's devtools throttling: 3.5 s.** On "slow 4G" it is 2.1 s. The
   critical path is HTML → 209 kB of JS (≈ 1.2 s at 1.47 Mbit/s) → first render. With 562.5 ms per round trip,
   connection set-up and requests add ≈ 2 s. Proposals, cheapest first:
   - serve precompressed brotli (−26 kB, −13 %);
   - take `tailwind-merge` (≈ 20 kB gzip) and the sync/catalog libraries out of the preloaded chunk;
   - inline the login shell (HTML/CSS skeleton), so FCP does not wait for JS.
3. **Explorer search for a rare term: 246 ms, half of it walking all 93k submissions newest-first.** The `OR`
   between `number ILIKE`, the value semi-join and the submitter semi-join defeats early termination. A UNION of
   matching uuids as one semi-join measured 33 ms vs 44 ms for the count; not changed because exports share
   `ReportScope::search`. Watch it at 500k+.
4. **Saved report over a whole large form: 365 ms (p95) at 100k.** It grows linearly: two heap scans of
   `submission_values` (392 MB) per view. At about 150k submissions per form the page would cross 500 ms.
   Proposals:
   - cache the result per viewer for the dashboard TTL, as pinned reports already do;
   - or a covering index `(form_id, key) INCLUDE (submission_uuid, value_num)` for numeric metrics (index-only
     scans).

   Dev Postgres runs with default settings (shared_buffers 128 MB): the first view after a restart is ~2× slower.
5. **Dashboard: Filament's notification mailbox lock** (footnote ²) adds ~250 ms to one of three parallel
   widget requests. That is vendor behaviour. Making the widgets non-lazy would avoid it, at the cost of a larger
   first response.
6. **Audit log at 150k entries** passes at 153 ms. The event filter walks the primary key backwards (75 ms when
   the newest entries have other events), and the subject-type filter options use `SELECT DISTINCT`, a 67 ms
   sequential scan per render. If the table grows into the millions, `(organization_id, event, id)` and
   `(organization_id, subject_type)` indexes are the fix. They were not added now: the table is append-only,
   high-volume and already has 9 indexes. (The audit log files belong to another agent's fix batch; any change
   should go through the orchestrator.)
7. **Adding a row to a 500-row repeater: median 203 ms at 4× CPU (192–225).** Typing stays below 200 ms.
   One evaluation of the whole form still costs ~29 ms on the laptop (Node), so ~115 ms at 4×. The rest is spread
   over React rendering and measuring the virtualized rows. Dexie (IndexedDB) work adds ~20 ms per addition (a
   browser CPU profile at 4×, three additions); presumably the autosave of the 501-row draft (inferred, not
   traced). Proposals:
   - skip the confirming settle round when no calculated value or default can change visibility (it repeats
     the whole evaluation);
   - run autosave's IndexedDB write after the next paint (`requestIdleCallback`).
8. **Fixtures vs. real data:** generated texts have a vocabulary of 200 "Name Word" pairs, so a 35 % hit rate
   for one word is a worst case. Generated drafts carry no attachments, and the PDF has synthetic photos.
