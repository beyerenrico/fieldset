# M13 Operability and release → 2.0.0: gate report (2026-10-20)

Architecture: ADRs 0089 (instance page, update check, backup alerts), 0090 (agent guide and its doc-test) and 0091
(dogfooding, CI journeys, pg_dump check) record the M13 decisions; the gate amended ADR 0083. The units ran in worktrees,
each merged with `--no-ff`: U20 31a617d, U21 511b3bb, U22 5b140c4. Gate fixes: 9151b36, bee8620 and the docs round
1843f97 (review), then 8bd1287 (the R51 guide run).

## What was built
### `/platform` instance page, update check, backup alerts (U20, M13-T01)
- `/platform/instance` (operators only): problems first (backup alerts with the `fsa` command that helps,
  `backup_silent`, disk under 10 % / 5 % free, update available, "backups are held only on this host"), then version
  and image digests, mode and URL, mail with the catcher link (R23) and `fsa config show --catcher-login` in the loopback
  modes, backups, disk and updates. DE and EN (R53).
- The app learns the instance facts through `runtime.json` (`instance` and `updates` blocks, parsed leniently), so the
  app never loads ops code (KTD24).
- `fsa config set update-check on|off` (E15, off by default). On, `instance:check-updates` runs daily at 04:17: one GET
  of the release manifest URL (`fsa upgrade`'s URL), 10 s / 30 s timeouts, at most 1 MiB, only `version` and `notes_url`
  read; "update available" with the notes link and `fsa upgrade` (R48). Off means no HTTP call on any path.
- Backup alerts (R39): every `BackupAlerts` code is mailed once per incident to every active operator in their locale
  (hourly `instance:backup-alerts`), and stays on the instance page. The gate fixed a silent drop: an incident is
  remembered only after at least one mail was queued (9151b36).
- The instance page no longer claims "up to date" before a check found the newest release (bee8620).

### Agent guide, 2.0 guides, RELEASING.md (U21, M13-T02)
- `docs/guide/agent-guide.md` (R51): rules for agents, the envelope, exit codes and one reading order for recovery
  fields (QUESTIONS 69 O5, documented rather than unified), and recipes: local demo, sign-in links, SMTP, backup and
  restore (drill, encrypted, warnings), upgrade and rollback, move to another server, VPS install, phone demo, change
  the domain, remove an instance, a failed install. It ships as a release asset (`release.yml`).
- Runnable blocks are marked `sh runnable` with a `json expect` block after them; J11 runs them in order against the
  local release (ADR 0090). `GuideReferencesTest` checks every `fsa` command and flag, install.sh flag, artisan command,
  environment variable and relative link in README.md and `docs/guide/`.
- install, upgrade, backup/restore, configuration and troubleshooting guides rewritten for `fsa` (R52); the 1.0 guides
  moved to `docs/guide/archive/1.0-*.md` with a warning not to use them on an `fsa` instance. README quick start is the
  one-liner. `RELEASING.md` completed: first publish, signing and secrets, the stable-only update check, the pg_dump
  check, and the real-world checks still to run.

### Dogfooding, CI journeys, pg_dump check (U22, M13-T03)
- `DogfoodE2ETest`: the E2E suite runs against a local-mode `--demo` instance installed by install.sh from the local
  release (`E2E_TARGET=fsa`, artisan through `docker exec` into the instance's app container, Mailpit behind its
  generated login). Journeys that need dev-only services skip there and keep running on the dev stack (see Gate
  results).
- CI job `install-journeys` (ubuntu-24.04, 300 min): all install journeys with Playwright and poppler, failing instead of
  skipping when Docker or Playwright is missing; creates the local `v1.0.0` tag for J9 when the remote has none.
- `release:check-pg-dump` (R39): the app image's `pg_dump` major must be at least the manifest's Postgres major; runs
  in `release.yml` and in the local harness.
- J10 measures the backup service at the 1.0 data volume (unreclaimable peak 77.7 MiB of its 128 MiB slot, no OOM).

## Deviations
- The R51 subagent ran on this machine with the repository present: it was told to read only the guide copy and a lab
  sheet and to use only the commands' own `--help` (BUILD_PROMPT_V2 §15.6 asks for no repository access). Its instance
  directories were named `forms…`, so its Docker resources were `fsa-forms-…`, not `fsa-test-…`; it created and removed
  them all.
- The update check reads `latest`, so pre-releases never show as updates (RELEASING.md;
  [ADR 0089](../../adr/0089-instance-page-and-update-check.md)).
- The update check lives in `App\Domain\Platform\Instance\Updates`, not `App\Domain\Instance\Updates` as the plan named
  it: the latter is ops code the app may not load ([ADR 0089](../../adr/0089-instance-page-and-update-check.md)).
- `backup_silent` shows on the page but is not mailed ([ADR 0089](../../adr/0089-instance-page-and-update-check.md)).
- The recovery fields stay as they are; the guide documents one reading order (QUESTIONS 69 O5,
  [ADR 0090](../../adr/0090-agent-guide-doc-test.md)).
- J11 runs the guide against harness releases (`2.0.0-rc.1-test`), and upgrades only to the installed version; the
  real upgrade ran in the R51 run ([ADR 0090](../../adr/0090-agent-guide-doc-test.md)).
- E16 targets are measured on Docker Desktop, not on a VPS; admin pages and one API series miss
  ([ADR 0083](../../adr/0083-e16-resource-budget-measurement.md), QUESTIONS 41, 74).
