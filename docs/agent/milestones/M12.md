# M12 Lifecycle → 2.0.0-rc.1: gate report (2026-10-20)

Architecture: ADRs 0084–0088 record the M12 decisions: 0084 (backups), 0085 (restore, drill, `--from-backup`), 0086
(upgrade and rollback), 0087 (adopt) and 0088 (reset). Each carries amendments of 2026-10-20 from later units and from
the gate. The gate also amended 0072, 0073 and 0078. The units ran in worktrees, each merged with `--no-ff`: U16 ac804bc
and e629d6d, U17 be7b56b and 45213cd, U23 a650d68, U19 ea98143, U18 48630b6. The gate fixes ran in three worktree

## What was built
### Backups (U16, M12-T01)
- A `backup` service in every stack: the app image, container root with four capabilities, no Docker socket, the
  storage volume read-only. Daily at 03:30 instance time, keep 7 scheduled backups (E13).
- `fsa backup` writes a backup now while the instance keeps running. `--include-secrets` adds APP_KEY and the SMTP
  account and needs encryption (exit 2 otherwise).
- One exported Postgres snapshot feeds `pg_dump --snapshot`, the audit chain heads and the file-reference query; then
  the storage archive. A manifest names versions, the migration set and the audit epoch.
- `SHA256SUMS` and an HMAC keyed from APP_KEY are written last. A run counts as a success only after the checksums,
  `pg_restore --list` and the file-reference check.
- Retention prunes only scheduled backups after a successful run. Manual, kept, safety and final backups stay. A run
  that would fill the disk is skipped with a warning.
- `backup_runs` is written through the insert-only role `fsa_backup`. `fsa status` and the `/platform` health check
  show the last run, the schedule, the backups on disk and alerts.
- Encryption: `fsa config set backup-encryption on` creates an age key pair. The identity goes outside the instance,
  encrypted with the passphrase (batchpass), and a decrypt test runs. Only the public key stays.
- `fsa config set backup-schedule` and `backup-retention`.
- `audit:verify --heads` reports the chain epoch (`ChainEpochTest`).
- Memory: the service peaked at 68 MiB in J08, inside its 128 MiB slot, so no new J10 run (ADR 0084).

### Restore, drill and `--from-backup` (U17, M12-T02)
- `fsa restore <backup>` after confirmation, as journaled phases with resume and `--abandon`:
  - decrypt and check in a one-off without network or socket; a safe tar reader rejects absolute paths, `..`,
    symlinks and special files (`SafeExtractorTest`);
  - the HMAC is keyed only from APP keys outside the archive; `--accept-unauthenticated` is needed for failing or 1.0
    archives, which a restricted role restores and a schema audit checks;
  - quiesce and seal, the ledger, a safety backup, then a scratch database and a fresh storage volume;
  - epoch bump and `instance.restored`, the R64 security-state carry, sequences advanced, sessions, reset tokens and
    sign-in nonces cleared;
  - swap and Valkey flush, start, verify behind the gate, lower the gate.
- A failure before the swap is exit 5 with the old instance running; a failed swap-back is exit 8. A newer migration
  set is exit 7 and changes nothing (AE8).
- `fsa restore --drill` restores into a scratch database and reports counts, heads, missing files, a test render and
  a decrypt sample.
- `fsa install --from-backup`: portable settings from the backup, host-bound ones from flags, a pending certificate as
  a warning, capture mail and paused webhooks until confirmed. 1.0 `scripts/backup.sh` archives go through a `.env`
  allow-list with `--accept-unauthenticated`.
- `fsa config set webhooks on|paused`; restores leave webhooks paused.
- J08 found that the Valkey flush never worked: the image appends `VALKEY_EXTRA_FLAGS` (LEARNINGS 137). Fixed.

### Reset (U23, M12-T05)
- `fsa reset [--demo] [--no-backup]` under lock and journal: quiesce, seal, ledger with the final heads, safety
  backup (or, with `--no-backup`, an audit export while a real organization exists).
- The database is recreated (append-only triggers forbid truncation). Storage goes to a fresh volume; Valkey and
  Mailpit are emptied.
- Epoch bump and `instance.reset` with the old heads; install's seed phase runs again in one-offs. `--demo` follows
  the demo password policy. Settings and secrets stay.
- No terminal and no `--yes` is exit 6. A failure before the drop leaves the instance as it was (exit 5). After the
  drop only `fsa reset` continues (QUESTIONS 58). `fsa reset --abandon` ends a reset stopped before the drop.
- Sequences are raised to the old values, so old signed links find nothing. `app:install` became one transaction.

### Adopt a 1.0 install (U19, M12-T04)
- `fsa adopt <checkout>` (install.sh `--adopt`): checkout read-only, allow-listed `.env` keys. A Compose override, an
  external database or a Postgres other than 16 on Alpine is exit 7.
- KTD20 order: stop and drain 1.0, a 1.0-format backup (APP keys named by fingerprint only), a clean Postgres stop,
  copy into labelled volumes in a one-off, verify counts, chain heads, migrations and amcheck on the unique text
  indexes, then start 2.0 on `postgres:16-alpine`.
- Mode inferred from `APP_URL`/`APP_PORT`; APP_KEY kept; unsafe values (`SSO_ALLOW_INSECURE_IDP` and others) never
  applied. Any failure before 2.0 starts brings 1.0 back (exit 5). `--abandon` undoes a half-done adopt.
- Uninstall of an adopted instance takes a final backup by default and reports the writes since adopt and how to
  start 1.0 again.

### Upgrade and rollback (U18, M12-T03)
- `fsa upgrade [--to] [--major] [--drop-jobs] [--resume]`, run by a detached supervisor container of the installed
  image (KTD5). Killing the foreground leaves it running (J7).
- The target's signed manifest is verified, every image pulled, a space check runs (exit 3).
- Quiesce: gate up, scheduler and backup stop, Horizon drains (exit 9 `drain_timeout` unless `--drop-jobs`, which
  saves the payloads), in-flight requests end, `audit:seal`. A verified safety backup follows (exit 9 if it fails).
- The target's `fsa` runs as a socket-less child: it renders compose and env into staging, which is validated, and
  runs migrations with `lock_timeout`, zero foreign connections and a liveness probe; a hung child is killed and
  rolled back.
- Start behind the gate, smoke test, commit, open. Any failure from the safety backup to the commit rolls back
  through U17's atomic path (exit 5); a failed rollback stops the instance (exit 8, R55).
- `fsa rollback`: quiesce, seal, ledger, a versioned R64 export, states the data loss first. It refuses after a
  restore or reset and refuses an older `--to` (exit 7).
- Older backups (fsa and 1.0) restore in place through the child (phase `upgrade_child`, ADR 0085 amendment).
- A migration lint refuses `CONCURRENTLY` in upgrade migrations (`UpgradeMigrationLintTest`).

## Gate fixes
- **Round A (27b9a64): backups, security, data safety.**
  - S1: a `.partial` set stays root's until complete; `SHA256SUMS` lists only the files the writer created and
    hashed through its own descriptor; anything else fails the run (`set_changed`).
  - D1: fsa never removes `safety-rollback-*` sets or kept ones; a commit removes only older `safety-upgrade-*`.
  - Final backups (DOC12, D3, C10, DOC6/7/15): uninstall's final backup is a 2.0 backup (kind `final`), encrypted
    when encryption is on; plain sets get the APP keys beside them. `fsa install --from-backup` and `fsa restore`
    read it.
  - D2: uninstall quiesces before the final backup and restarts what ran on failure.
  - D4 and EV3: a backup without files is refused in place unless `--without-files`, which keeps the replaced
    volume. J09's "59 of 59 missing" was load-generator renditions without files, now asserted.
  - D5: `backup_files_missing` warns, and retention holds back while files are missing.
  - S2: the service reads settings from the new private `staging/`, not `backups/`; `--from-backup` keeps
    recipients only with `--keep-recipients`.
  - S3: no plaintext in `backups/` (staging for plain sets, restore scratch, rollback export).
  - D6 fsync before hash, rename and unlink. D8 carry window `>=` and branding logos as references.
  - S4: a renamed set is refused (`backup_renamed`); rollback checks the safety backup's digest
    (`safety_backup_changed`). S5: reset's audit export is encrypted. S6: hardened one-offs (`no-new-privileges`,
    `--cap-drop ALL`, read-only root file system).
- **Round B (60d7f2d): recovery, operability, docs.**
  - O1: a plain `fsa install` no longer takes over a from-backup journal (exit 9).
  - O2: resume lines rebuild `--identity-file`, passphrase source, `--app-key-file`, `--accept-unauthenticated`,
    `--without-files`, `--keep-recipients` and `--yes`; a resume lacking an input exits 2 before the lock.
  - O3: the supervisor's result stays; `fsa upgrade --follow`; `--resume` with nothing open is exit 2
    `nothing_to_resume`; `fsa status` shows `last_upgrade`.
  - O4: `operation.state` running or interrupted, `supervisor`, `lock.stale`.
  - O6: exit 6 carries `data.question` and its facts. O7: empty passphrases and `install.sh --passphrase-stdin`
    without a terminal are exit 2. O8: restore, rollback and adopt run under the interruption guard. O9 hints carry
    `--yes`. O10: every envelope carries a numeric `exit_code`.
  - C2: a rollback leaves webhooks paused. C3: closing paths seal every plaintext safety set since the journal began.
    C4: unfinished operations are reported before questions; the drill takes the lock. C5: restore does not restart
    the quick tunnel. C6: rollback hint. C11: login-link during a scheduled backup.
  - D7: a resumed restore or rollback whose writers ran retakes ledger and safety backup.
  - DOC13/14/16: hints name runnable commands (`install.sh --dir <new> --from-backup`, no `fsa fsa`).
  - EV2: J09 restores the adopt's 1.0 backup in place through the upgrade child.
  - ADR and CHANGELOG corrections (DOC4/5 among them).
- **Round C (b2f719f): the verification review of round A.**
  - R1 (high, pre-existing): restore-time TOCTOU. A plain set was verified in place, then `pg_restore` read it by
    path. Now the fixed file list is copied into `staging/restore-<id>/set` and only that copy is verified and read
    (LEARNINGS 158).
  - R2: uninstall has the backup service remove root-owned partial sets (`fsa backup-daemon --clean`) and names what
    it cannot remove (`files_left`).
  - R3: the retention hold lasts while files are missing, at most two held backups.
  - R4: a failed quiesce in uninstall restarts the stack and lowers the gate.
  - R5 (encrypted final set moves unauthenticated) is a design question: QUESTIONS 70.
- A host restart killed rounds B and C before their final runs; they were finished by hand (JOURNAL).

## Deviations
- `fsa upgrade` without `--to` targets `latest` (the newest stable release), not the newest within the installed major
  (R33). A new major is exit 7 naming `--major` or `--to`
  ([ADR 0086](../../adr/0086-upgrade-and-rollback.md), QUESTIONS 65).
- J7 runs between harness releases `2.0.0-rc.1-test` and `rc.2-test` (plus `rc.3-test` unhealthy and `rc.4-test`
  crashing), not `2.0.0-rc.1` → `2.0.0` as the plan says: `ReleaseVersion` accepts no `2.0.0-test`
  ([ADR 0086](../../adr/0086-upgrade-and-rollback.md)).
- Queue, scheduler and backup do not themselves refuse to start behind the gate (plan U18). A host reboot during an
  upgrade restarts only the app ([ADR 0086](../../adr/0086-upgrade-and-rollback.md), QUESTIONS 64).
- An older backup's migrations run before the restore's new epoch, not after it as the plan's order says
  ([ADR 0085](../../adr/0085-restore.md) U18 amendment).
- An interrupted reset continues only with `fsa reset`; other changing commands answer exit 9 naming it (plan: "on
  the next `fsa` command") ([ADR 0088](../../adr/0088-reset.md), QUESTIONS 58).
- R39's operator notifications for failed backups are not built; `fsa status` and `/platform` show the failure.
  Notifications belong with the U20 instance page ([ADR 0084](../../adr/0084-backups.md)).
- `fsa install --encrypt` is refused; encryption is turned on after the install
  ([ADR 0084](../../adr/0084-backups.md), QUESTIONS 52).
- Adopt copies the 1.0 volumes (R60 replaces R46's in-place takeover). Going back to 1.0 is `docker compose up -d` in
  the checkout, not R46's full-restore procedure. A Postgres other than 16 on Alpine is refused
  ([ADR 0087](../../adr/0087-adopt.md), QUESTIONS 61, 62).
- An encrypted final backup moves only with `--accept-unauthenticated`: its APP key is inside it
  ([ADR 0073](../../adr/0073-uninstall-final-backup.md) amendment, QUESTIONS 70).
- A new top-level `staging/` directory (0700, never synced) holds the backup service's settings and every plaintext
  working copy. Safety backups stay plain in `backups/` until sealed ([ADR 0084](../../adr/0084-backups.md) and
  [ADR 0085](../../adr/0085-restore.md) amendments).
- A restore of a plain backup needs space for one more copy of its dump and storage archive (R1 fix,
  [ADR 0085](../../adr/0085-restore.md) amendment).
- A backup without files is refused in place unless `--without-files`; `--from-backup` keeps recipients only with
  `--keep-recipients` ([ADR 0085](../../adr/0085-restore.md) amendments, QUESTIONS 71).
- The root-owned partial set protects nothing on rootless Docker and Docker Desktop, where container root is the owner
  ([ADR 0084](../../adr/0084-backups.md) amendment, QUESTIONS 72).
- `--from-backup` gives the new instance a new UUID, so the predecessor's backups do not restore in place there
  ([ADR 0085](../../adr/0085-restore.md), QUESTIONS 54).
