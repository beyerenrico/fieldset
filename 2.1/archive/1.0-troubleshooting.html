Archive (1.0): Troubleshooting ​

Archive. This is the 1.0 guide for an installation from a clone of the repository with Docker Compose (a "checkout install"). It describes 1.0 under the product's former name, form-schema-app; the product is now Fieldset. It does not apply to an instance installed with install.sh and managed with fieldset (2.0): do not run its git, docker compose, migration, restore or .env steps on such an instance; they bypass fieldset's backups, maintenance gate and rollback. For 2.0 see the current guide. To move a checkout install to 2.0, use fieldset adopt (install guide).

Start with the general checks, then find your symptom below. Commands assume the Docker Compose installation from the install guide, run in the project directory.

Contents:

General checks ​

bash
docker compose ps                                     # app and queue "healthy", scheduler and gotenberg running
docker compose logs --since 30m app queue scheduler   # JSON logs, one object per line
curl -fsS http://127.0.0.1:8080/up                    # the application boots (not a database check)
docker compose exec queue php artisan horizon:status  # "Horizon is running."
docker compose exec app php artisan queue:failed      # failed jobs
docker compose exec app php artisan schedule:list     # scheduled tasks and their next run
docker compose exec app php artisan migrate:status    # every migration "Ran"

Platform operators (the owner created by app:install, others granted with php artisan app:platform-admin) can open the Horizon dashboard at /horizon after signing in at /platform/login (password and MFA) to see queues, failed jobs and their errors; an /admin session alone is not enough. Platform operators see the same checks on one page at /platform → "Zustand" ("Health"): Horizon, failed jobs, Gotenberg, mail, scheduler and disk space.

If logs are missing from docker compose logs, .env probably has LOG_CHANNEL=stack with LOG_STACK=single from .env.example; the logs are then in storage/logs/laravel.log inside each container. Set LOG_STACK=json (as in .env.production.example) and recreate the containers.

After any change to .env: docker compose up -d --force-recreate app queue scheduler.

The dashboard looks broken behind HTTPS ​

Symptoms: the admin dashboard loads without styles or does not react, the browser console reports "mixed content", SSO redirect URIs start with http://, or all users share one login rate limit.

Cause: the application does not trust the reverse proxy, so it sees plain HTTP and the proxy's IP address. TRUSTED_PROXIES must contain the address the proxy connects from. For a reverse proxy on the host that connects to 127.0.0.1:8080, that is the Docker bridge range 172.16.0.0/12 from .env.production.example. An empty value trusts no proxy. Recreate the containers after the change. Details: install guide, step 5.

Also check that APP_URL starts with https://, and that the proxy forwards the Host header and sets X-Forwarded-Proto.

The reverse proxy cannot reach the app. compose.yaml publishes the app port on 127.0.0.1 only, so the proxy must run on the same host and connect to 127.0.0.1:<APP_PORT>. APP_PORT is a port number only; a value such as 127.0.0.1:8080 from older guides breaks the port mapping.

Every page answers 400 Bad Request ​

Unless APP_ENV is local or testing, the application answers only to the host name of APP_URL, loopback names and the names in TRUSTED_HOSTS. Any other Host header, or X-Forwarded-Host from a trusted proxy, gets 400. Fix APP_URL, or add the extra name to TRUSTED_HOSTS (comma-separated), then recreate the containers.

PDFs are not created (Gotenberg) ​

"Das PDF wird erstellt …" ("The PDF is being created…") does not go away. PDFs are created by the queue. Check the queue first. The scheduler's documents:sweep re-dispatches PDFs that are missing after 10 minutes, so a short queue outage heals by itself.

The submission shows "PDF-Erzeugung fehlgeschlagen" ("PDF generation failed") in the admin inbox under "Dokumente". There is no separate notification for this; the Field App shows that the office was informed. The panel names the reason:

  • "Das Dokument ist zu groß für die PDF-Erzeugung (zu viele oder zu große Fotos)." The document with all its photos exceeds the render budget (DOCUMENTS_MAX_REQUEST_BYTES, 25 MB). Use fewer or smaller photos, or raise the budget together with Gotenberg's --api-body-limit (30 MB in compose.yaml).

  • "Der PDF-Dienst konnte das Dokument auch nach mehreren Versuchen nicht erzeugen." Gotenberg was unreachable or failed on three attempts in a row. Check Gotenberg:

    bash
    docker compose ps gotenberg
docker compose logs --since 1h gotenberg
docker compose exec app curl -fsS http://gotenberg:3000/health     # {"status":"up",…}

    app and queue reach Gotenberg over the internal renderer network; GOTENBERG_URL must stay http://gotenberg:3000. Gotenberg has no internet access on purpose.

After fixing the cause, click "PDF neu erzeugen" ("Re-render PDF") on the submission. Customer emails that were waiting for the failed PDF were not sent; send them again after the new PDF exists.

"PDF-Vorschau" ("Preview PDF") fails with "Die Vorschau konnte nicht erzeugt werden." The preview is rendered while you wait, so the same Gotenberg checks apply.

Mail is not sent ​

Look at "E-Mail" → "E-Mail-Protokoll" ("Mail log") in the dashboard:

StatusMeaning and fix
"In Warteschlange" ("Queued") for minutesThe queue is not running (below). A mail whose earlier attempt failed temporarily also waits here for the next attempt.
"Fehlgeschlagen" ("Failed")Open the mail to see the error, fix the cause, then "Erneut senden" ("Send again"). Mail is tried 3 times before it fails.
"Fehlgeschlagen" with "Delivery was interrupted; the mail may or may not have been sent."A worker stopped while sending. Check with the recipient before sending again.
"Gesendet" ("Sent") but nothing arrivedThe SMTP server accepted it. Check the spam folder and the SPF/DKIM/DMARC records of MAIL_FROM_ADDRESS's domain.

Common causes:

  • MAIL_MAILER is not set: the default log writes mails to the log instead of sending them.
  • Wrong MAIL_HOST, MAIL_PORT or credentials: the error is in the mail log or the container logs.
  • An organization's own SMTP server: "Dieser Mailserver ist nicht erlaubt. Er muss über eine öffentliche Adresse erreichbar sein." means it resolves to a private address; only public servers on ports 25, 465, 587 and 2525 are allowed.
  • "Test-E-Mail senden" only queues the mail; the result appears in the mail log, and only if the queue runs.

Invitations and password-reset mails do not appear in the mail log. Look for errors in docker compose logs app queue.

The queue does not run ​

Symptoms: PDFs stay "being created", mails stay "In Warteschlange", workflows do not start, notifications and exports do not arrive, PDF imports never finish.

bash
docker compose ps queue
docker compose exec queue php artisan horizon:status   # running, paused or inactive
docker compose logs --since 1h queue
docker compose up -d --force-recreate queue
  • QUEUE_CONNECTION must be redis; with the framework default database, jobs go to a table that Horizon does not work.
  • Exports pending but everything else works: the supervisor-exports supervisor is missing. Recreate the queue container with the current image. It runs one export at a time, so a large export delays the next.
  • Failed jobs: docker compose exec app php artisan queue:failed, then retry with php artisan queue:retry <id> or in the Horizon dashboard.
  • DOCUMENTS_QUEUE, MESSAGING_QUEUE or WORKFLOWS_QUEUE set to a custom name: no supervisor works that queue unless you add one to config/horizon.php.

The scheduler does not run ​

Symptoms: scheduled workflows and review reminders stop, scheduled report emails do not arrive, export files are not deleted, missing PDFs are not re-dispatched, SSO health checks stop.

bash
docker compose ps scheduler
docker compose logs --since 1h scheduler
docker compose exec app php artisan schedule:list

The scheduler service has no health check, so check its logs: workflows:tick runs every minute.

Field App ​

Work stays "Wartet auf Synchronisierung" ("Waiting to sync"). The device tries every minute while the app is open, on reconnect and on "Jetzt synchronisieren" ("Sync now"), with longer pauses (up to 15 minutes) after errors. Ask the worker what the header shows:

Header or messageCauseWhat to do
"Erneut anmelden, um zu synchronisieren"The session expired, or the device check failed (also when the device was rate-limited). Automatic syncing pauses.Sign in again in the app; the data stays on the device.
"Brauchen Ihre Entscheidung: N"The server refused something, for example a retired form version, revoked form access, or a draft over the 2 MB limit.The worker opens the item and follows the instructions (Field App guide).
"Nicht gespeichert – der Speicher dieses Geräts ist voll."The device is out of storage.Free space; sync; install the app.
Nothing, the app is just offlineNo connection. On iPhone and iPad the app only syncs while it is open.Open the app once online.

What an administrator can check:

  • whether the submission already arrived in "Einreichungen";
  • server errors (5xx) or rate limiting (429) in docker compose logs app;
  • the queue, because the PDF and the customer email follow the sync;
  • SESSION_LIFETIME (43200 minutes keeps devices signed in for 30 days).

Do not use "Geräte sperren" ("Revoke devices") to fix a stuck device: the device then deletes all local data, including unsent work.

Sign-in does not stick, or every request fails right after sign-in. Check that the host name of APP_URL is in SANCTUM_STATEFUL_DOMAINS, that SESSION_SECURE_COOKIE=true is only used over HTTPS, and that the Field App is opened on the same host as APP_URL.

"Die Formulare sind offline noch nicht verfügbar." The device has not downloaded the forms yet; connect once.

The app does not offer to install, or offline mode does not work. The site must be served over HTTPS. On iPhone and iPad, install from Safari's share menu.

Single sign-on ​

Administrators get "Single Sign-on erfordert Ihre Aufmerksamkeit: <provider>" ("Single sign-on needs your attention"). The hourly provider check or the daily domain check failed; the SSO page shows the status "Fehler" ("Error") and the last error. The notification names the reason, for example:

  • the discovery document, the signing keys (JWKS) or the SAML metadata could not be loaded: check the issuer or metadata URL and that the server can reach the provider over HTTPS;
  • issuer, tenant, audience or signature mismatches: compare the issuer, tenant ID and client ID with the provider's settings; for SAML, the provider's signing certificate in its metadata;
  • invalid_client: the client secret is wrong or expired; enter a new one;
  • a domain lost its verification: the TXT record is gone or changed;
  • the break-glass Owner is no longer valid (deactivated, no longer Owner, or no two-factor authentication), so enforcement has no emergency access.

The same problem is reported at most every 6 hours. Run the check by hand: docker compose exec app php artisan sso:check-providers. A successful check sets the status back to "Aktiv".

Users see the password step instead of the identity provider. The email domain is not verified, or the provider is not active yet (run "Anmeldung testen", "Test sign-in").

Domain verification fails. "Kein TXT-Eintrag gefunden" ("No TXT record found"): the record is missing, not yet visible (DNS caching), or was created as _form-schema-app-verification.example.com.example.com because the DNS provider appended the domain; then enter only _form-schema-app-verification as the name.

The provider reports an invalid redirect URI. Register exactly the redirect URI shown on the SSO page (https://<your server>/auth/sso/<id>/callback). If it starts with http://, see the HTTPS note.

Users come back with an error. The login screen explains it; the codes are sso_failed, sso_denied, account_inactive, not_member (no membership and just-in-time provisioning is off), domain_not_verified, email_unverified (the provider does not mark the email as verified) and provider_unavailable.

"Ihre Organisation schreibt die zentrale Anmeldung vor." ("Your organization requires single sign-on.") Password login is turned off for this domain. Only the break-glass Owner can still use a password. If the identity provider is down, the break-glass Owner signs in with password and two-factor code and can turn enforcement off.

Lost two-factor device. Sign in with one of the recovery codes, then set up two-factor authentication again in the profile.

Forgotten password. "Passwort vergessen?" Not available for addresses whose organization enforces SSO.

Signed out of the dashboard. Admin sessions end after 30 minutes without activity and 12 hours after sign-in at the latest (configuration). Sign in again. Field App sessions are not affected.

Uploads are refused by the malware scan ​

Only when UPLOADS_CLAMAV_ENABLED=true (configuration).

Answer to the uploadCause and fix
503 scanner_unavailableclamd did not answer. Check that it runs and that UPLOADS_CLAMAV_HOST and UPLOADS_CLAMAV_PORT are reachable from the app container. The Field App tries the upload again later.
422 file_infectedclamd found malware. The log has an upload.infected warning with the signature name, not the file.
422 file_too_largeThe file is larger than clamd's StreamMaxLength. Raise that limit in clamd (attachments may be up to 25 MB).

Audit log ​

audit:verify reports a problem. See When audit:verify fails. Right after an upgrade from 0.x it reports unsealed entries until audit:seal has sealed the older ones.

activity_log is append-only in the logs. Something tried to change or delete audit entries, and the database refused it. Retention pruning uses audit:prune. Do not use activitylog:clean: the database refuses it too.
